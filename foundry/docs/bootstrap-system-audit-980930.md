# Системный аудит bootstrap после билда 980930

Дата: 24 сентября 2026. Проверены текущий код Foundry, workflow и сохранённые
артефакты билдов 980641/980930. Новые вызовы провайдеров и CI-прогоны не запускались.
Это аудит устройства процесса и фактического прогона, а не подтверждение исправности
сгенерированного кода. Полный локальный replay пока не завершён.

Главный вывод: процесс слишком поздно получает исполняемое доказательство,
а до этого оплачивает подготовку большого объёма связанных документов и кода.
Восстановление после остановок улучшилось, но оно не подтверждает сходимость
генерации и не ограничивает денежный риск.

## Находки и критерии закрытия

### P0. Денежный расход не ограничен

**Подтверждено кодом.** `config/project.yaml`, `ai.run_budget.max_total_tokens`:
325 млн токенов. Временной предел relay — отдельный механизм. Оценка USD
формируется отчётом и не используется для допуска вызова.
Утверждение, что существуют только временные ограничения, было неточным:
токенный предел существует, но не является денежным.

`Invoke-Stage.ps1::Assert-AgentBudget` проверяет уже записанный расход.
`Invoke-Agent.ps1::Invoke-AgentProviderCall` не резервирует стоимость перед
каждым внутренним повтором/repair. Параллельные вызовы могут стартовать на одном
остатке; supervisor вызывает Invoke-Agent напрямую. Эти пути означают возможный
перерасход сверх порога, а не доказанный обход лимита в 980930: здесь порог
вообще не был достигнут.

**Закрытие:** единый допуск всех вызовов с резервированием в общем журнале,
согласованный USD-предел на всю цепочку и лимиты стадий; остановка при неизвестной
стоимости. Проверки параллельного старта, repair, supervisor, resume и kill.
Если CLI не позволяет ограничить расход внутри одного вызова, нельзя называть
локальную проверку перед запуском абсолютным денежным пределом: нужен предел
на стороне биллинга/провайдера либо честно указанное возможное превышение.

### P0. Исполняемая обратная связь появляется слишком поздно

**Наблюдалось.** `workflows/bootstrap-automation.yaml`: полная verification —
стадия 12 из 13. Implementation и ранний code review работают с описаниями
будущих файлов. Delivery review прямо признаёт, что файлы ещё не собраны.
Это не поддельные approvals, но они не снижают риск несовместимого кода.
До первого compiler feedback уже потрачены $64–77 только в последнем билде.

**Закрытие:** после выбора стека сначала материализовать минимальный работающий
набор каждого проекта: manifest, реальные support API, один содержательный
локальный тест, точный runner и negative probe. Проверить его до массовой
генерации сценариев и повторять сборку после завершённых групп зависимостей.
Ревью фактического кода и подготовки доставки проводить на проверенных байтах.

### P0. План и verifier имеют разные контракты запуска

**Наблюдалось.** NuGet adapter запускает MTP через `dotnet run` без category
filter; план описывает `--filter TestCategory=EnvironmentFree`.
Npm adapter запускает `npm test`; первоначально скрипта не было, затем repair
связал его с тем же `playwright test`, что и `test:deployed`.
Само наличие категории не задаёт выбор тестов по умолчанию.

**Закрытие:** один машинно-проверяемый контракт local/deployed команд, используемый
планом, generator, verifier и CI. До генерации всех тестов выполнить точную local
команду без целевых credentials; проверить непустые assertions и negative probe.
Deployed-проверки сохранить и запускать отдельно с реальными prerequisites.
Последнее исправление инструкций агентам полезно, но ещё не доказывает совместимость.

### P1. Генератор не получает быстрой проверки применённого API

**Наблюдалось и подтверждено устройством.** CLI разрешён только `view`;
проверка компилятором происходит позже через deterministic action.
Toolchain smoke доказал restore/minimal build, но не использование каждой
сигнатуры SDK. Несовместимые MSTest assertions, RabbitMQ constructor и неоднозначные
перегрузки пережили генерацию; RabbitMQ остался сломан после целевого repair.

**Закрытие:** compiler feedback на работающем наборе зависимых файлов и доступные
генератору сигнатуры именно locked SDK. Исправление принимается после сборки,
а не по тексту «repaired» в summary. Расширять разрешения модели на произвольный
shell для этого не требуется: проверку может выполнять оркестратор.

### P1. Критерий прогресса допускает бесконечное улучшение документов

**Подтверждено кодом; бесконечный цикл здесь не доказан.**
`scripts/helpers/relay-progress.mjs`: новая комбинация пути/хеша принятого артефакта
обнуляет `noProgressLegs`. Новый корректный JSON может не приближать проект
к успешному тесту. Все три verification оставались красными.

**Закрытие:** отдельно измерять сохранённую работу и технический результат:
проекты restore/build/test/probe, устойчивые идентификаторы ошибок и новые
регрессии. Повтор той же ошибки после repair должен останавливать этот repair
или менять его способ в пределах бюджета. Не требовать монотонного уменьшения
числа compiler errors: исправление синтаксиса иногда впервые открывает другие.

### P1. Независимая генерация файлов оплачивает большой повторный контекст

**Наблюдалось.** На 69 авторских файлов — 119 вызовов стадии generation:
71, 41 и 7 по итерациям, включая planner/retries. Последняя итерация сохранила
63 файла и ремонтировала 6: сохранение результата уже работает, полного
перегенерирования на каждом repair здесь нет.
Generation использовала 152.9 млн токенов, но стоила $27–29;
на остальные стадии ушло $47–60. Снижение только числа генераций не устраняет
большую часть расходов этого билда.

В одном записанном вызове — 5.57 млн токенов при request-файле 136 KB.
CLI-сессия включает дальнейшие обращения/чтения, поэтому размер request-файла
не ограничивает всю стоимость. По этим записям нельзя точно разделить стоимость
отдельных внутренних чтений; конкретный источник каждого повторения не доказан.

**Закрытие:** контекст по контрактам и непосредственным зависимостям файла,
повторное использование утверждённых решений и сравнение затрат на успешно
проверенный проект. Не возвращаться к огромному JSON всех файлов: это уже
приводило к truncation. Сначала измерить уменьшение контекста на сохранённом случае.

### P1. Учёт не даёт верхней границы при аварии

**Подтверждено кодом.** Usage собирается после выхода CLI, metadata пишется
в finally; ошибка записи даёт warning. Жёсткое завершение процесса может не
исполнить finally. Нечитаемые записи пропускаются; fallback bytes/4 не учитывает
внутренние запросы CLI. Отчёт явно помечает учёт неполным.

**Закрытие:** до запуска писать устойчивую запись started с уникальным invocation
ID и резервом; завершать её reported/unknown. Не превращать unknown в малую
достоверную стоимость и не отпускать резерв после resume без сверки.
Итоговые USD сверять с биллингом, не выдавать текущий диапазон за гарантированный максимум.

### P1. Проверки механики подменяли уверенность в конечном результате

**Наблюдалось.** Падение supervisor вызвано путём к вложенному snapshot,
не проверенным прежними mock-прогонами. Последние 38 тестов и rehearsal проверяют
runtime/recovery, а не сборку сгенерированных проектов. В сохранённом результате
нет доказательства успешного окончания оставшихся стадий доставки.

**Закрытие:** хранить воспроизводимый проблемный change set и прогонять настоящий
restore/build/test/probe на CI-платформе без модели. Отдельно проверять real-provider
adapter через управляемый fake CLI, смену leg, исключение supervisor и восстановление
диагностики. Финальное review/apply/регистрацию проверять изолированно, с проверкой
повторного выполнения. Mock-тесты остаются полезными, но не являются доказательством
успеха автономного прогона.

### P2. Ошибка prerequisite запускает платный анализ продуктовых дефектов

**Наблюдалось.** После UI preflight failures вызван `failure-investigation`:
один вызов, около $1.07–1.15. `Report-ProductDefects.ps1` отбирает failed cases,
а различение setup/product передаёт модели. В этом случае продукт не был проверен.

**Закрытие:** структурированный результат preflight и deterministic классификация
известных setup failures до LLM. Не объявлять продуктовую ошибку только по слову
в логе и не скрывать реальные assertion failures при смешанных результатах.

### P1. Успех Foundry и доказательство работы продукта — разные результаты

**Подтверждено артефактами.** Целевые URL, identities, broker grants и browser
provisioning остаются внешними prerequisites. Даже будущий зелёный local run
подтвердит работу локального harness, а не deployed API/UI/Messaging сценариев.
На данный момент нет ни полного local успеха, ни deployed-доказательства.

**Закрытие:** раздельные статусы generated / compiled / local verified /
deployed verified / delivered и стоимость достижения каждого. Не показывать
11/13 стадий как вероятность близкого успеха. Для вероятности успеха с первой
попытки нужен набор независимых полных прогонов; имеющаяся цепочка её не оценивает.

## Порядок работы до следующего платного прогона

1. Завершить локальный разбор сохранённого change set, исправить C# и контракт
   запуска. Пройти все три настоящие сборки, непустые local suites и negative probes.
   Не менять исходные evidence и не ослаблять deployed assertions.
2. Ввести учёт и допуск расходов на всей цепочке; согласовать денежный предел.
   Проверить параллелизм, внутренние повторы, supervisor и прерывание без модели.
3. Сделать раннюю проверку работающего набора файлов и контракт команд обязательными;
   прогнать её на сохранённых примерах. Не увеличивать число legs/повторов как лечение.
4. Проверить recovery и оставшуюся доставку в изоляции. Зафиксировать точные хеши
   проверенного кода: новое решение модели после проверки снова требует проверки.
5. Только затем рассматривать ограниченный платный эксперимент. Его стоимость
   и проверяемая гипотеза должны быть известны заранее; успех с первого раза
   не обещается и не выводится из числа зелёных runtime unit tests.

Это предложенные критерии, не выполненные исправления. В рамках аудита изменён
только этот документ. Новый CI-прогон не поставлен в очередь.
